# Проект следующей версии для проверки Astra

База: выпущенная 0.4, aa8d2a5, чистое дерево. Следующий выпуск: 0.5.0-guide, code 5. Реализация еще не начата

## Что подтвердили разведка и оркестратор

- В 0.4 есть перевод/оригинал/смысл, ручной поиск, короткий on-device ASR, автопрокрутка фраз и отдельные переходы этапов
- Геопоиск ограничен двумя приходами в радиусе 500 м, точность хуже 500 м отвергается. Нет поиска города, избранного и собственного храма
- Предложение расписания только на сегодня и в пределах -150/+120 минут. Сохраненное чтение может скрывать его. Следующая утренняя служба вечером не видна
- Этапы и фразы имеют независимые таймеры, намеренно взаимоисключенные. Равные 8/12/16 секунд не учитывают длину строк
- 18 этапов занимают редакционные 104 минуты, из них подготовка 5 и сама литургия 99. Это не измеренные средние
- Данные фрагментарны: Великая ектения 12 слов на 4 минуты, анафора 19 слов на 12 минут. Нельзя распределять их на весь этап и называть реальной скоростью
- Чтения есть только на 2026-11-08. Отсутствующий текст нельзя заменять другим днем
- Исходная сборка и unit-задача проходят; кэшированные проверки 0.4 не считаются новыми результатами 0.5

## Предлагаемый объем и порядок

0. Сохранить релиз 0.4, работать в codex/feoria-0.5-service-player
1. Закончить исследование и проверку Astra, затем NIGHT_PLAN и коммит
2. Три отдельные законченные правки
   - 2.1 Храмы в поездке: поиск среди добавленных по городу/названию, избранное, добавление собственного храма, явная геопривязка, часовой пояс. Дополнительно исследуется внешний поиск храмов по явному запросу с ограниченным ожиданием/кэшем и без фоновой отправки координат. Если внешний источник непригоден - честное ограничение, поиск в установленной карте и ручное добавление
   - 2.2 Текущая/следующая служба: ближайшая в доступном подтвержденном периоде, дата/время/часовой пояс/происхождение. Собственное время литургии на конкретную дату, не подмена официального расписания. Приблизительная текущая служба не означает доказательство фактического проведения
   - 2.3 Одна основная кнопка "Смотреть службу": краткий порядок с выделенным предположением, затем текст. Сохраненное чтение отдельно. Порядок доступен в шапке текста; ручной вход без расписания сохранен
3. Единственная крупная фича - цельный приблизительный плеер
   - Чистая единая модель времени и переходов до интеграции в UI. Одна основная Play/Pause, явно видимый режим/темп
   - Оригинал / По-русски / Смысл в одном доступном переключателе с сохранением фразы. Для текста без оригинала нельзя показывать ложный оригинал
   - Автопереходы между текстами/этапами после явного включения, ручные переходы всегда доступны
   - Реальная скорость хора неизвестна. Время этапов сохраняет статус редакционной оценки; доступны медленнее/обычно/быстрее, изменение сохраняет долю текущего интервала
   - Текст не растягивается на весь этап: окончание доступного фрагмента -> понятное ожидание, затем приблизительный следующий этап. Отсутствующее чтение дня -> пауза, ручное продолжение; не проскакивать Апостол/Евангелие из одного возгласа
   - Монотонный clock для движения во время видимого экрана, wall clock только для расписания. Фон/выход/смысл/поиск/уточнение останавливают движение и сохраняют место, восстановление без самопроизвольного запуска
   - Требуется решение Astra о конкретной модели cadence и незавершенного этапа до реализации
4. Отдельный прототип микрофонного сопровождения и решение допуска. Android SpeechRecognizer официально не предназначен для непрерывного распознавания; короткий ASR сохраняется. Без реальных акустических данных и надежного API автоматический режим нельзя объявлять стабильным. Прототип должен проверять неоднозначность/повторы/границы и не менять пользовательский runtime без прохождения gate
5. Три цикла UX: вход/расписание; чтение/плеер/уточнение; ошибки/нетсети/темнаятема/крупныйшрифт/ландшафт. Разделение зон цветом поверхности и отступами, сохранить спокойную фирменную палитру, не имитировать iOS-декор
6. Полный QA, независимый Astrareview, версия/changelog, подписанный APK прежним ключом, actual upgrade 0.4->0.5, RELEASE v0.5.0, проверка сборки и доставка. После stop-критерия прекратить правки

## Вопросы для математической и логической проверки

1. Приемлем ли ограниченный каталог с внешним search и ручным временем как законченный сценарий поездки, какие запреты на происхождение/время нужны?
2. Как безопасно связывать stage-score и line cadence при фрагментарных данных, не выдать искусственную синхронизацию? Предложи конкретную минимальную архитектуру
3. Что обязательно проверять на границах даты, DST, смене скорости, фоне, пропусках и восстановлении?
4. Какие части нужно уменьшить/отложить ради стабильности? До положительного решения runtime не меняется
