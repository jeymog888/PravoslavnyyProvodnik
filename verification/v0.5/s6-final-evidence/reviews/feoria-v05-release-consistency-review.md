## Как честно разделить RELEASE commit и будущие факты

Предложенное root разделение корректно: отдельный выполненный пункт "Подготовлена финальная ревизия RELEASE" и отдельный статус сборки/доставки по delivery.json. Не отмечать единый старый checkbox "собрано и доставлено", пока обе части еще впереди

Простая формулировка для документа в финальном commit, после фактического принятия CI:

"Этот документ фиксирует проверки кандидата и состав финальной ревизии. Результат сборки этой ревизии, опубликованный APK и проверка скачивания фиксируются отдельно в delivery.json соответствующего GitHub Release. До появления успешной записи доставки выпуск не считается завершенным"

В delivery.json нужны наблюденные значения, а не будущий PASS: commit, tag, APK SHA/size, build receipt/source identity, asset URL, время и результат скачивания. Если место для ссылки нужно в неизменяемом RELEASE commit, ссылка на страницу соответствующего GitHub Release может быть задана заранее как ожидаемое место отчета, с явной пометкой о будущем заполнении. Не создавать фиктивный delivery.json со статусом PASS до фактов

Исторический production-identity.json на e8ad6a0 не переименовывать в identity финального commit. Его scope уже правильно ограничен "Before final release documentation commit". Финальный receipt/delivery добавляет новую привязку отдельно
