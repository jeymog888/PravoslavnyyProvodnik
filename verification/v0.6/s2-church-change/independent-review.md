## R7 - точная семантика overflow и новый критерий читаемости

Проверены классы точных `ui-text-android:1.7.3` и `foundation-android:1.7.3`; временные jar сверены SHA-256 с classes.jar внутри AAR из dependency cache и полностью совпадают

`TextLayoutResult.didOverflowWidth` вычисляется исключительно как `size.width < multiParagraph.width`, без измерения видимых букв. `didOverflowHeight` проверяет maxLines либо `size.height < multiParagraph.height`; `hasVisualOverflow` объединяет эти два признака

Для обычного String Text в 1.7.3 SemanticsActions.GetTextLayoutResult вызывает `TextStringSimpleNode.applySemantics` -> `ParagraphLayoutCache.slowCreateTextLayoutResultOrNull`. Этот метод создает новый MultiParagraph по prevConstraints с обнуленными minimum constraints, но сохраняет старый layoutSize в итоговом TextLayoutResult. Поэтому семантический MultiParagraph может иметь всю разрешенную ширину, а Text - только собственную ширину строки. Разность может быть значительно больше субпикселя и означать пустую часть абзаца, а не обрезание текста

R7: у "Остаться" size.width=544, maxWidth=763, высота совпадает с paragraphHeight=173, height overflow=false. Эти данные согласуются с описанным механизмом, но сами по себе не сообщают lineRight. Называть эту конкретную ошибку доказанным округлением на 1 px нельзя. Нативный PNG независимо показывает полностью видимую подпись и отсутствие прежнего наложения двух действий

Корректный oracle уже есть в `ReaderAccessibilityTest.kt:303`:

1. Сохранить строгую проверку actual density.fontScale=2.99
2. Проверить отсутствие didExceedMaxLines и ellipsis
3. Проверять каждую реальную строку: lineLeft/top >= -1 px, lineRight <= size.width+1 px, lineBottom <= size.height+1 px. Допуск относится только к границам строк, а не к разрешению произвольного paragraph overflow
4. Для title/buttons проверить полную видимость через visible и unclipped bounds с допуском одного физического пикселя
5. Для самих кнопок проверить минимум 48 dp, отсутствие пересечения друг с другом и viewport сообщения, а также нахождение в доступной области окна
6. Body намеренно прокручивается, поэтому полный body не обязан целиком входить в viewport одновременно. Его строки должны укладываться в собственную layout area, а прокрутка до конца сообщения должна оставлять действия видимыми и доступными

Такой oracle не является слепым ослаблением: он проверяет реальное обрезание и наложение, не принимает декоративную свободную ширину реконструированного абзаца за текст. При lineRight больше допустимого размера либо неполной видимости кнопки надо исправлять layout, а не увеличивать допуск

Отдельное наблюдение PNG R7: нижняя кромка Surface/скругление не видна, а "Остаться" находится близко к полосе жестов. Буквы визуально целые, но это не доказательство полной видимости области нажатия. Поэтому новый bounds oracle необходим до окончательной приемки; проверку нельзя ограничить line extents. Изменение дизайна без установленного нарушения bounds не требуется. Если bounds выходят за видимое окно, адресно ограничить высоту/учесть insets нового диалога

Итог: текущая failure по didOverflowWidth не доказывает реальный clipping. Обоснованная замена test oracle - ACCEPT; окончательный large-font PASS до измерения line extents, bounds и прокрутки не присваивается

`availableHeight` вычисляется снаружи Dialog по outer LocalConfiguration.screenHeightDp за вычетом top/bottom safeDrawing. Это сохраняет связь с текущим окном приложения, а не с повторно созданным dialog owner.
