# Расширение текстов 0.6 и сохраненное чтение 0.5

Дата: 9 ноября 2026
Роль: explorer, только чтение. Исходники, тесты, Gradle, adb и git-состояние не менялись

## Рекомендация

Для ограниченного дополнения Великой ектении, анафоры и Трисвятого предпочесть новые соседние `StageText`, сохранив существующие `type`, оригиналы, состав и порядок строк внутри прежних текстов. Это позволяет не вводить новую схему явных ID. Но все равно нужна отдельная миграция строго известного плана 0.5: проверить его настоящий fingerprint, прочитать старую позицию в старом плане и перенести смысловой адрес в новый. Нельзя заменять hash и оставлять прежний segmentIndex

Миграция должна сохранять дату, контекст храма, язык и скорость. Для прежней неизмененной строки можно сохранить точный elapsedQuarterMillis. Для измененного ожидания точной эквивалентности нет: вернуть последнюю известную строку на паузе с коротким уведомлением о дополненных текстах, а не выдавать пересчитанное ожидание за прежнее положение службы

## Проверенные механизмы

- `PrayerTrackFactory.build`: prayer track ID = stage ID + kind + первые 12 байт SHA-256 от `text.type` и всех оригинальных строк текста через перевод строки. Каждая line ID начинается с полного track ID и включает hash своей исходной строки. Повторы получают суффикс по порядку встречаемости
- Поэтому вставка даже одной строки ВНУТРЬ старого текста меняет ID текста и всех его прежних строк. Изменение только русского изложения, title, explanation, source или isExcerpt не меняет ID при неизмененном original
- `ServicePlaybackPlan.build`: глобальный fingerprint включает contentVersion, дату и каждый сегмент по порядку. Для Text это stage/track/line ID, длительность и канонический исходник; для Wait - stage и длительность; для MissingReading - stage и дату; для End - stage. Добавление отдельного текста меняет глобальный hash и числовые позиции последующих сегментов
- `CONTENT_VERSION=1` обозначает семантику сегментов/темпа. Одно добавление контента не требует повышения этой константы: изменения фактического контента уже покрывает hash. Если меняется сама семантика, исторический план необходимо строить с прежней версией, а не переименовывать новый план в старый
- `ServicePlaybackSnapshot`: только contentVersion, planFingerprint, segmentIndex, elapsedQuarterMillis, speed. В snapshot нет stage/track/line ID. Контекст хранится рядом в `StoredServicePlayback`
- `ServicePlaybackEngine.restore/isValid`: требует точного совпадения contentVersion/hash, допустимого индекса и `0 <= offset < duration`. У MissingReading и End offset=0, autoplay запрещен. Восстановление всегда на паузе
- `ServicePlaybackStore.restore`: сначала проверяет строгий codec, равенство полного ReadingContext и даты плана, затем engine.restore. Любое изменение контента сейчас дает PLAN_MISMATCH. Наличие даже испорченного snapshot блокирует LegacyPlaybackMigration - этот защитный контракт нельзя обходить удалением ключа
- `ReadingAcceptanceStore.acceptPlayback`: одним commit сохраняет context/snapshot/session/stage/current bookmark. UI меняется после успешного commit; отказ делает одну попытку rollback. `resetBookmarks=false` сохраняет остальные закладки и настройки
- `PlaybackBookmark` содержит stage/track/line ID. В Wait/Missing/End он отражает последний текст текущего этапа, но не доказывает, на каком из этих сегментов стоял плеер. Старые `lyric_offset_*` не являются offset нового snapshot: 0.5 записывает в них 0
- `MainActivity`: обычный Valid snapshot инициализирует player прямо; legacyCandidate принимается через beginReading и writer. Для кандидата миграции нужен второй путь, чтобы до успешной атомарной записи его не объявить уже принятым сохранением
- Долговечно хранится `lyric_original` для оригинала/русского. "Смысл" в 0.5 - `rememberSaveable` внутри ServiceScreen, не поле preferences. Его сохранение после обновления пакета нельзя обещать как существующее свойство 0.5. Сохранение при обычной навигации/пересоздании - отдельный контракт

Файл ServicePlaybackPlan.kt в текущем дереве побайтно совпадает с выпущенным v0.5.0-guide, SHA-256 `c5ef19a3be0040535b2030cf7ca061fc208760f20b39aba48c1fd3400923849c`. Проверен peeled commit тега: `98302858e341d8de621f7a1d87fce6d24b23db6b`

## Что позволяет текущий контент

Великая ектения действительно состоит из двух ОТДЕЛЬНЫХ однострочных текстов: "Миром Господу помолимся" и "О свышнем мире". Можно вставить новый ответ хора между ними, а после второго - новый согласованный блок дальнейших прошений и ответов. Старые тексты при этом неизменны. Не обязательно превращать каждую новую строку в отдельный track

Анафора: один старый текст содержит пару "Горе имеим сердца / Имамы ко Господу", другой - три строки "Тебе поем". Проверенные слышимые блоки можно расположить до, между и после этих двух текстов. Сами существующие пары не разрывать только ради удобства данных

Трисвятое: старый текст - одна строка с `isExcerpt=false`. Если источники подтверждают нужную последовательность повторений, сохранить эту строку первым прежним текстом, добавить следующие части после нее. Повторяющиеся новые идентичные тексты нельзя вставлять перед прежним: изменится значение суффиксов occurrence. Исправление признака полноты/пояснения само по себе fingerprint не меняет

Все эти дополнения требуют отдельной содержательной проверки. Здесь оценена только техническая совместимость, не подтверждена богослужебная редакция

## Минимальная архитектура миграции

### 1. Точная историческая база

Зафиксировать выпущенные assets 0.5 как неизменяемые ресурсы только для миграции, с commit и SHA в тестах/описании. Полные liturgy_stages.json и daily_readings.json сейчас занимают вместе 102563 байта до сжатия - небольшой и прозрачный объем для APK. Это проще и надежнее восстановления старого плана путем вычитания новых строк из текущих данных

Для сохраненной `context.serviceDate` строить исторический план теми же 0.5 правилами и только с чтением той же даты. Для 8 ноября 2026 есть чтения, для других дат - прежние MissingReading. Не использовать сегодняшнюю дату и не подставлять чтение 8 ноября на другую дату

Текущий алгоритм плана/Factory допускается переиспользовать лишь пока его семантика 0.5 сохранена; обязательные золотые тесты fingerprint для опубликованного дня и дня без чтений не позволят незаметно изменить историческую интерпретацию позже. При изменении алгоритма историческая реализация должна остаться явной

### 2. Строгий допуск

Сначала обычное восстановление нового плана. Только если оно не подходит, после строгого decode и полного context/date equality проверить snapshot через engine именно исторического плана 0.5. Unknown hash, другая contentVersion, чужой храм/дата/зона/источник, несуществующий индекс или offset вне старой длительности остаются Invalid. Не использовать закладки как доказательство неизвестного snapshot

Мигратор может быть маленькой чистой функцией `oldPlan + newPlan + validated stored snapshot -> candidate/rejection`. Зависимость чтения historical assets остается снаружи. Не нужен универсальный реестр миграций или новая схема snapshot 2 для этой итерации

### 3. Перенос по типу сегмента

| Старая позиция | Условие | Результат |
|---|---|---|
| Text | В новом плане найдены те же stage/track/line ID, тот же канонический исходник и длительность | Новый segmentIndex по ID; ТОЧНО прежний offset и speed; paused |
| Wait, этап не менялся | Совпадает полная последовательность канонических сегментов ЭТОГО этапа, включая Wait, несмотря на сдвиг global index | Новый Wait того же stage; точный прежний offset/speed; paused |
| Wait, этап дополнен | Старый Wait корректен, но новые тексты сокращают/убирают/перемещают ожидание | Последняя известная старая строка через ее ID, offset=0, прежняя speed, paused; заметка "Тексты дополнены. Вернули к последней сохраненной фразе" |
| Wait без старой строки и с измененным этапом | Нет надежного адреса | Явное ручное восстановление, без угадывания следующего этапа |
| MissingReading | В новом плане есть та же преграда stage/date | Та же преграда, offset=0, paused. Если преграда исчезла из-за нового чтения, нужен отдельный явный recovery, не автоперескок |
| End | Сохранился конец того же последнего этапа | Новый End, offset=0, paused |

Почему не сохранять старый Wait offset автоматически: после добавления текста `W = max(0, D-C)` сокращается. Прежнее значение может стать недопустимым; пропорциональное масштабирование, clamp к последнему миллисекундному остатку или перенос "общего времени этапа" приписали бы новое значение неопределенному положению. Это не сохранение фактического исполнения. Консервативный возврат к известной строке честнее и не запускает движение сам

Сопоставление только по одинаковому тексту без track/line ID небезопасно: одинаковые ответы встречаются в разных этапах и несколько раз внутри одного этапа

### 4. Принятие и сохранение

Результат read-only restore обозначить отдельно как MigrationCandidate с новым корректным snapshot и необязательной заметкой об измененном ожидании. Не подавать его в initial accepted player как обычный Valid до записи. При открытии сохраненного чтения принять через существующий beginReading/writer/ReadingAcceptanceStore с `resetBookmarks=false`. После commit=true показать новый reader на паузе; после commit=false старые данные остаются, показывается существующая ошибка, а кандидат не выдается за сохраненный

Контекст и язык сохраняются без пересчета. Совместимый session marker должен соответствовать новому stage, autoAdvance=false и elapsedInStageMillis=0. Новый snapshot сохраняет новый hash и новый индекс. Повторный запуск уже идет через обычный Valid путь, миграция не повторяется

При варианте новых соседних текстов существующие track/line ID и внутренние индексы старых текстов не меняются. Поэтому остальные bookmarks сохраняются без массовой перезаписи; текущий bookmark нормализуется существующим atomic writer

## Альтернатива: явные стабильные ID

Опциональные ID у StageText/PrayerLine с прежним hash fallback возможны, если содержательно правильный текст нельзя выразить соседними блоками. Для прежних строк нужно сохранить ТОЧНО вычисленные 0.5 ID, новые ID должны быть уникальны и проверяться, а не молча получать суффикс. Первая итерация такой схемы обязана давать побайтно те же планы и fingerprints до изменения контента

Но это затрагивает модель, parser, Factory, валидацию, тесты и совместимость старых числовых bookmarks внутри изменяемых текстов. Глобальная миграция snapshot все равно нужна. Для трех текущих дополнений эта цена пока не оправдана. Схема 2 с semantic address могла бы упростить будущие обновления, но не умеет задним числом добавить адрес в сохранение 0.5 и не нужна для узкой миграции

## Проверки перед приемкой

1. Золотые планы выпущенного 0.5 на 8 ноября и на дату без чтений; их fingerprints и отдельные snapshots зафиксированы от release, а не пересоздаются только новым кодом в expected
2. Для КАЖДОГО старого Text сегмента: после вставок до/между/после старых текстов тот же stage/track/line, тот же offset на 0, внутреннем значении и duration-1, каждая из трех скоростей, всегда paused
3. Старые числовые segmentIndex реально сдвигаются, но semantic address остается прежним. Тест должен ловить ошибочное копирование индекса
4. Wait неизмененного этапа сохраняет offset; измененный Wait возвращает известную строку на паузе с заметкой; крайние старые offsets и исчезновение Wait не перескакивают вперед
5. MissingReading остается преградой на сохраненную дату. End остается концом. Нет подмены даты, календарного catch-up и автостарта
6. Любое неизвестное/измененное старое содержимое, чужой контекст, некорректная версия, индекс или offset отклоняются; present malformed snapshot по-прежнему блокирует legacy import
7. При отказе commit и rollback сравнить весь затронутый набор preferences; настройки и чужие bookmarks сохранены. При успешной записи повторный restore не является новой миграцией
8. UI: открыть сохраненное чтение после изменения assets, проверить строку/дату/язык/speed, обычный resume и явную заметку для измененного Wait; возврат на главный экран не запускает Play
9. Нативное обновление настоящего подписанного опубликованного APK 0.5 -> 0.6 без очистки данных: как минимум Text с ненулевым offset после изменяемого раннего этапа и Wait в изменяемом этапе. Проверка только специально подготовленных XML не заменяет upgrade
10. Legacy 0.4 bookmarks и обычный 0.6 restore остаются рабочими. При выбранном варианте соседних tracks внутренние старые индексы/IDs проверяются на неизменность

Сборки и тесты в этой разведке не выполнялись. Все варианты выше требуют решения оркестратора и независимого ревью до реализации
