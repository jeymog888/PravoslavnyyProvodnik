# Микрофон 0.6: доступность, надежность и допуск синхронизации

Дата проверки: 9 ноября 2026
Роль: explorer/reliability, только чтение кода и документов
Исходники, тесты, устройство и зависимости не изменялись. Gradle и adb не запускались. Ниже отделены прежние свидетельства от новых выводов по коду

## Вывод для пересмотра плана

В 0.6 есть полезный и ограниченный шаг: сделать короткое локальное распознавание видимым прямо из reader, объяснить его состояния и подготовку телефона, сохранить подтверждение найденного места человеком. Это улучшает настоящую функцию, которую пользователь не смог найти

Непрерывное автоматическое сопровождение пока не прошло допуск: runtime для него отсутствует, реальной акустической выборки нет, текстовый matcher имеет доказанный контрпример ложной привязки. Ни добавление кнопки, ни повторение циклов SpeechRecognizer, ни новая порция синтетических тестов не закрывают эти три пробела

## Что точно существует

- `SpeechGuide.kt:34`: одна попытка, запущенная человеком, не более 15 секунд захвата и затем до 5 секунд ожидания результата. Окончание речи может завершить захват раньше
- Создается только `createOnDeviceSpeechRecognizer`. Перехода к сетевому распознавателю нет. Аудиофайл не записывается
- Транскрипт временно хранится в состоянии UI. Сопоставление происходит только при `SpeechStatus.RESULT`; partial может показываться, но не выбирает этап
- `ListeningCard.kt:69`: после совпадения есть кнопка "Открыть этот этап". Само совпадение не двигает плеер
- Отмена увеличивает `sessionId`, освобождает recognizer, очищает транскрипт. Поздние callbacks старой попытки отбрасываются. ON_STOP вызывает stop, dispose вызывает destroy
- В manifest есть RECORD_AUDIO и queries для RecognitionService. Foreground service, его разрешения и непрерывный аудиодвижок отсутствуют
- `HypothesisPrototype` находится только в test sources. Он выдает `CandidateForReview`, не имеет ссылки на плеер и всегда возвращает `automaticSyncEligible=false`

## Почему пользователь не увидел микрофон

Точный путь из reader сейчас: "Уточнить" -> "Поиск по словам" -> "Подсказка по звуку" -> "Послушать фрагмент". Первые две подписи не сообщают про микрофон. Источник: `ServiceScreen.kt:234`, `ManualMomentScreen.kt:45`, `StageSelector.kt:78`, `ListeningCard.kt`

В `StageSelector` карточка целиком находится под условием `searchMode && query.isBlank()`. После ввода любой непустой строки исчезают и вход, и открытая карточка. При ошибке поиска человек видит возможность очистки, но не альтернативу "послушать"

При `UNAVAILABLE` внутри ListeningCard нет кнопки запуска: показано только объяснение. Это корректно по возможности устройства, но из внешнего UX все случаи - функция скрыта, отсутствует, требует подготовки - смешиваются

Существующие UI-тесты даже закрепляют отсутствие "Послушать фрагмент" до раскрытия: `GuideNavigationTest.serviceOrderIsSeparateFromSearchAndOptionalListening`. Это подтверждение прежнего контракта, а не доказательство удобства

## Поддержка платформы

| Условия | Поведение текущего APK | Значение для продукта |
|---|---|---|
| API 26-30, хотя приложение устанавливается | `isOnDeviceAvailable=false`, запуск не предлагается | Android 8-11 поддерживают само приложение, но не текущий локальный микрофон |
| API 31-32 | Проверяется наличие on-device сервиса; затем делается реальная попытка ru-RU | Android 12 сам по себе не гарантирует готовую русскую модель |
| API 33+ | Та же проверка сервиса, без `checkRecognitionSupport` | Можно заранее различать готовую модель, доступную загрузку, ожидание загрузки и неизвестную поддержку |
| API 34+ | Дополнительные word timing/confidence не запрашиваются | Эти необязательные данные сами по себе не доказывают положение службы |

On-device factory появилась в API 31; проверка поддержки запроса и базовая загрузка модели - в API 33. Методы recognizer вызываются на main thread; объект освобождается через destroy. Общее предупреждение Android про непрерывное распознавание относится к SpeechRecognizer API и не является запретом на любую локальную streaming-архитектуру. Оно не дает гарантий непрерывности конкретному сервису. [SpeechRecognizer](https://developer.android.com/reference/android/speech/SpeechRecognizer)

API 33 различает установленные локальные языки, ожидающие загрузки и поддерживаемые, но еще не скачанные. Эти списки нельзя объединять в "готово". [RecognitionSupport](https://developer.android.com/reference/android/speech/RecognitionSupport)

`EXTRA_PREFER_OFFLINE` может игнорироваться провайдером; сейчас локальность правильно обеспечивается factory. `EXTRA_SEGMENTED_SESSION` появился в API 33 и зависит от реализации, поэтому установка флага не создает переносимый непрерывный режим. Word timing/confidence в API 34 также optional. [RecognizerIntent](https://developer.android.com/reference/android/speech/RecognizerIntent)

Для будущего фонового захвата при target 35 потребуется foreground service типа microphone с соответствующими manifest-разрешениями и RECORD_AUDIO. Такой сервис обычно нужно запускать из видимого приложения из-за while-in-use ограничений. Сейчас архитектура сознательно прекращает короткую попытку при уходе. [Foreground service types](https://developer.android.com/develop/background-work/services/fgs/service-types#microphone)

## Ограничения определения места

`PhraseMatcher.kt` сопоставляет полные нормализованные фразы с границами слов. Он отбрасывает общие реплики, повторяющиеся прошения ектений, одинаковые якоря разных этапов и транскрипт с несколькими различными этапами. Уникальность внутри неполного справочника не равна уникальности на настоящей службе

В 18 этапах нет якорей у подготовки; якоря большой ектении специально исключены как повторяющиеся. Поэтому распознавание не может уверенно определять абсолютно каждую часть даже при идеальном ASR

В текущем matcher нет вероятности, уверенности ASR, акустической модели, оценки расстояния от текущей фразы или понимания цитирования. Повтор одной и той же гипотезы не дает независимых свидетельств. Добавлять процент уверенности по длине строки или числу повторов было бы неверно

Контрпример уже закреплен тестом `quoted prayer is a candidate and a counterexample to automatic synchronization`: разговор "Вчера пели Иже Херувимы тайно образующе" дает `cherubic_hymn`. Для подсказки, проверяемой человеком, это известное ограничение; для автоматического прыжка плеера - ложное срабатывание

Позиция по этапу и позиция по фразе - разные уровни. Успешное узнавание "Иже Херувимы" может подсказать этап, но не подтверждает все последующие секундные переходы. Переключение "Оригинал / По-русски / Смысл" должно менять представление одной принятой позиции, а не создавать новое распознавание или заново вычислять прогресс

## Предлагаемые маленькие итерации 0.6

### A. Сделать существующую возможность очевидной

- В reader добавить постоянно доступный подписанный вход "Микрофон" рядом с уточнением места; визуальный приоритет согласовать с общим новым reader, без еще одной конкурирующей primary-кнопки
- Tap открывает сразу экран или sheet короткого распознавания. Сам tap входа не включает запись. На экране ясно: "Послушать до 15 секунд" и один запуск. Так разрешение запрашивается в понятном контексте
- В поиске и ручном уточнении тот же вход доступен независимо от введенного запроса. Ввод текста не скрывает возможность и не запускает запись
- Если устройство не поддерживает режим, вход сохраняется как объясняющий экран с явным ручным действием. Не показывать вечный disabled-микрофон без причины
- После результата показывать "Похоже, сейчас ...", услышанную фразу и "Открыть этот момент". Отмена возвращает прежние храм, дату, фразу, режим и скорость. Возврат не включает Play
- При открытии из плеера использовать его существующий контракт корректировки/паузы, а не создавать новое чтение с текущей календарной датой

### B. Развести готовность и ошибки

Понятные состояния: подготовка, слушаем, проверяем фразу, найден кандидат, не разобрали, нет доступа, нет локального сервиса, русский язык не готов. Слушание и обработка имеют видимую кнопку "Выключить микрофон"; нажатие отменяет попытку и поздний результат

API 33 support check может улучшить подготовку, но должен иметь свой конечный срок, обработку unsupported/error и stale-generation защиту. Ошибка проверки не должна превращаться в бесконечное ожидание или в ложное "русский готов". Для API 31-32 оставить корректную bounded-попытку и ее ошибки

Если добавлять загрузку русской модели, делать это отдельным явным действием с наблюдаемым состоянием; не считать успешный вызов triggerModelDownload фактом готовности. После возврата из настроек повторно проверить готовность, а не оставлять старое UNAVAILABLE до переоткрытия

### C. Допуск continuous отдельно от кнопки

Не переносить test-only HypothesisPrototype в APK только ради видимости работы. Следующий существенный результат - проверка настоящего аудиодвижка на размеченном звуке с журналом предложенных переходов без управления пользовательским плеером. Только затем обсуждать автоматическое принятие позиции

Фоновый режим, уведомление со Stop и удержание обработки при блокировке - следующая отдельная итерация после качества акустики, а не способ исправить распознавание. Нет оснований добавлять тяжелую модель или service в текущую сборку без измерения потребления/качества

## Проверяемые сценарии A/B без обещания акустического качества

1. Из Text, Wait, Meaning и MissingReading микрофон находится без перехода через текстовый поиск; текст кнопки и accessible name однозначны
2. Введенный неудачный поиск не убирает альтернативу микрофона; возвращение сохраняет запрос
3. API 26/30 показывает понятное ограничение и рабочую ручную альтернативу; API 31/32 не вызывают API 33
4. Доступный сервис + русский отсутствует, требуется загрузка, скачивается, готов, support query error/timeout - разные проверяемые ветки через injected capability adapter
5. Нажатие запуска вызывает настоящий permission dialog, отказ не меняет чтение, повторный отказ не создает цикл запросов
6. Отмена на STARTING/LISTENING/PROCESSING, Back, Home, смена храма и пересоздание экрана отбрасывают поздние callbacks; одна попытка не отменяет более новую
7. Уникальный final, неоднозначный final, пустой final, partial->пустой final, язык unavailable, recognizer busy, audio error, timeout - управляемые сценарии через adapter. Ни один не изменяет чтение без принятия человеком
8. Принятый результат сохраняет serviceDate/выбранный режим/скорость и открывает существующий reader на паузе. Отказ сохранения не показывает ложный успех
9. Стоп не только меняет подпись: в нативной проверке исчезает активный захват, новый фрагмент после Stop не порождает результат. UI mock здесь недостаточен
10. Крупный шрифт/темная тема: статус, matched phrase, Stop и ручной выход читаются, не скрыты ниже непрокручиваемой области

Для этих изменений полезен узкий injectable speech/controller adapter и тестируемые переходы состояний. Не нужен новый универсальный фреймворк. Текущие callbacks Android и ресурсный cleanup должны остаться отдельно проверяемыми

## Протокол настоящего акустического эксперимента

Нужны записи разных голосов, хора, расстояний и помещений, включая повторы ектений, разговор с цитатой, проповедь, тишину, постороннее аудио и обрывки. Положительные куски размечать stage/phrase и интервалом реального произнесения. Отрицательные куски не размечать как ожидаемый следующий этап. Материал для настройки и контрольный материал разделить по целой службе/записи, чтобы соседние окна одного голоса не попадали в обе части

Для каждого прогона фиксировать: источник и хеш записи, разметку и ее версию, реальный девайс/API/распознаватель/версию модели/язык, способ подачи аудио, сырые ASR гипотезы в исследовательском журнале, кандидатов и причины принятия/отказа. Это отдельный эксперимент, пользовательские записи по умолчанию не сохранять

Метрики считать на звуке: ложные переходы в час, precision принятых переходов, доля пропущенных отличительных событий, задержка от окончания фразы до кандидата, доля времени без уверенной привязки, ошибки восстановления после ручной коррекции. WER полезен диагностически, но сам не показывает, уехал ли плеер на другой этап

Сначала режим наблюдения: кандидат пишется в журнал, плеер не двигается. Порог принятия фиксируется до контрольного прогона. Нельзя выбирать порог на той же записи, по которой сообщается точность, или выдавать отсутствие ошибок на нескольких фразах за надежность службы

Размер выборки должен соответствовать обещанию. Например, при 0 ложных переходов за T часов односторонняя 95%-граница пуассоновской интенсивности равна -ln(0.05)/T, примерно 3/T. Чтобы обосновать менее 0.1 ложного перехода в час в этой модели, понадобится около 30 часов, а не один удачный фрагмент. Предположение однородной независимой интенсивности для разных храмов может не выполняться, поэтому нужны также раздельные результаты по условиям. Это иллюстрация достаточности доказательств, не новое условие выпуска 0.6

Для native runtime отдельно проверять реальное локальное распознавание без сети, длительную нагрузку/нагрев/батарею, блокировку экрана, переключение приложения, аудиоконфликт, смену выбранного контекста и остановку из видимого UI/уведомления. Воспроизведение записи через динамик в эмулятор не равно акустике телефона в храме; injected text вообще не является ASR

## Итог допуска сейчас

- Видимый короткий микрофон и понятные состояния: реалистичный scope 0.6 после обновления плана и тестов
- Диагностика готовности русского языка: полезная ограниченная итерация, если не ломает API 31-32 и имеет конечное ожидание
- Непрерывные автоматические переходы: NO-GO на имеющихся свидетельствах. Конкретные недостающие основания - аудиодвижок/размеченный звук/проверенный критерий принятия и фоновые lifecycle-проверки
- Иллюстрации не устраняют ни проблему обнаружения микрофона, ни ложную акустическую привязку и остаются после основы
