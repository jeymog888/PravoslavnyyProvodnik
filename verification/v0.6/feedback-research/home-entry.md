# Шаг 2.2 - вход с главной и неизвестное расписание

Статус: read-only разведка. Исходники, тесты и план не изменялись. Gradle/adb не запускались
База: текущая ветка `codex/feoria-0.6-service-guidance`, незакоммиченный шаг 2.1 принят как текущий контракт guard

## Подтверждено в коде

- `MainScreen.kt:77-89`: выбран храм, обе рекомендации отсутствуют. В карточке неизвестного расписания главный filled Button сейчас `set_service_time` / "Указать начало литургии"
- `MainScreen.kt:96-103`: `find_stage` / "Найти текущий момент" находится отдельной строкой ниже. Простое добавление такой кнопки в карточку создаст дубль, поэтому строку нужно условно убрать вместе с ее divider
- `MainActivity.kt:361-365`: `openChurch()` всегда ставит `churchOrigin = MAIN`, при `church == null` увеличивает `churchPickerRequest`, затем открывает CHURCH
- `MainActivity.kt:406-408,426`: и нижняя вкладка, и карточка главной вызывают одну и ту же функцию. `churchOrigin` различить эти действия не может
- `ChurchScreen.kt:56-63`: успешный `onSelected` очищает черновик и закрывает picker, оставаясь на CHURCH. Все локальные способы выбора (список, фильтр, рядом, ручной храм) сходятся здесь
- `MainActivity.kt:557-564`: импорт с карты имеет отдельное завершение `chooseChurch(record.id) { onSelected(); navigate(CHURCH) }`. Без изменения этого места первый выбор через поиск не вернется на главную либо сделает два перехода
- `ChurchSelectionGuard`: callback выполняется только после успешного commit. PENDING, FAILED и STALE callback не вызывают. Это правильная общая точка завершения, ее нужно сохранить
- `navigate()` отменяет pending guard при каждом переходе. `cancelChurchSelection()` также вызывается при dispose ChurchScreen, в том числе при переходе из него в Discovery. Поэтому в этой функции нельзя безусловно очищать источник всего сценария выбора

## Минимальное изменение интерфейса

Ввести локальный предикат `unknownSchedule = church != null && overview.currentHypothesis == null && overview.nextKnownService == null`

В существующей карточке неизвестного расписания:

1. Сохранить честный заголовок "Нет данных о ближайшей литургии"
2. Пояснение перенести к действию, например: "Найдите место по словам молитвы или тому, что происходит в храме"
3. Filled Button "Найти текущий момент", существующий `onFindStage`, существующий уникальный tag `find_stage`
4. При ненулевом callback оставить TextButton "Указать начало литургии", tag `set_service_time`
5. Ниже сохранить "Порядок службы", но при `unknownSchedule` не выводить повторно строку поиска и разделитель над порядком

При невыбранном храме прежнее главное действие "Выбрать храм" остается. При известной службе прежнее "Смотреть службу" остается. Отсутствие callback личного времени не должно прятать поиск текущего момента

Это изменение не затрагивает расписания, даты, формулы и reading acceptance

## Минимальное изменение навигации

Нужен отдельный `rememberSaveable` маркер "первый выбор, начатый с главной". Не использовать `!hasChurchSelection`: восстановленный legacy храм уже может быть реально определен, хотя явного ключа еще нет. Условие первого выбора - `church == null`

- Вызов карточки главной выставляет маркер только если `church == null`
- Вкладка "Храм" выставляет обычный маршрут; известный храм с главной также остается обычным маршрутом
- `openPersonalTime()` для уже выбранного храма явно использует обычный маршрут
- Переход CHURCH -> DISCOVERY и возврат к picker сохраняют маркер. Закрытие листа или отмена подтверждения сами по себе не завершают сценарий
- Уход из всего сценария выбора в MAIN/SETTINGS/другой экран сбрасывает маркер. Новый вход всегда задает его заново. Не сбрасывать маркер внутри общего `cancelChurchSelection()`
- В `chooseChurch` до `guard.request` зафиксировать ожидаемое место завершения: MAIN при первом выборе с главной; CHURCH при обычном импорте из DISCOVERY; иначе без перехода
- Обернуть именно `onSelected`: сначала выполнить callback ребенка (закрыть picker/форму и очистить черновик), затем сбросить маркер и выполнить один нужный `navigate`
- Для Discovery удалить отдельный безусловный `navigate(CHURCH)`, передавая очистку формы в этот общий механизм
- Не вызывать переход по одному факту нажатия, сохранения записи каталога или результата PENDING. Только callback guard после успешного commit

Маркер должен пережить recreation, как остальные источники навигации. Старые callbacks по-прежнему отсеиваются guard; новую самостоятельную навигацию в них добавлять не нужно

## Визуальная приемка

Достаточно двух новых снимков: выбранный храм без расписания на обычном масштабе и при крупном тексте. Проверить разделение карточки места, карточки действия и списка порядка; единственное первичное действие; отсутствие дублирующего поиска; вторичное время достижимо. Не расширять шаг до редизайна остальных экранов

## Риск реализации

Главный риск - поставить возврат в `commitChurchChoice` или сразу после `request`: это ломает pending/ошибки и может навигировать до очистки дочернего черновика. Второй риск - очистить источник при `cancelChurchSelection`, который вызывается при техническом переходе в Discovery. Правильная граница - успешный callback guard и весь CHURCH/DISCOVERY сценарий
