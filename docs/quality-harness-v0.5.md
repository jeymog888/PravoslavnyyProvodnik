## Приоритет 1, P1: небольшой fail-closed runner

Реализация: Python standard library + существующий adb, версия инструмента в репозитории. Runner собирает доказательства и проверяет явные условия. Он не выносит автоматическое художественное заключение о дизайне

Минимальный контракт:

- Serial передается явно; нет неявного выбора первого устройства. Все вызовы adb адресуются этому serial и имеют ограниченный timeout
- Package передается явно и сверяется с установленным приложением. Действия ищутся внутри ожидаемого package. Системные permission dialogs допускаются только явно заявленным сценарием
- Selector должен находить ровно один enabled target. Если текст принадлежит не clickable дочернему узлу, определяется его ближайший подходящий enabled clickable ancestor; неоднозначные targets завершают шаг ошибкой. Нет молчаливого выбора первого совпадения или случайного тапания по координатам
- После каждого действия ожидается конкретный postcondition с deadline, используя монотонное время host. Сам успешный adb input не означает успешный переход
- Static capture снимается на паузе: XML before -> PNG -> XML after. Канонические XML ожидаемого app subtree должны совпасть; проверяются package и обязательные признаки состояния. Нормализация явно ограничена служебными различиями и не удаляет текст, selected/enabled, bounds или состояние плеера. При нестабильности допускается только ограниченный повтор, после deadline - ошибка. Совпадение XML доказывает только стабильность accessibility nodes, а не неизменность пикселей или visual PASS
- Dynamic capture является отдельным режимом: фиксируются оба XML, timestamps и движение/последовательность кадров. Ему нельзя присваивать статус стабильного визуального baseline
- Provenance: SHA-256 проверяемого APK, versionCode/name, package и build type; commit и хеш дерева исходников/dirty state на момент сборки; serial, API/SDK и build fingerprint; размер, density, font scale, locale, timezone и часы устройства; сеть и релевантные разрешения. Для release upgrade также certificate digest и SHA исходной 0.4
- Build receipt связывает APK с фактически выполненной сборкой: хеш набора build-input files до и после реального Gradle запуска, их равенство, команда, exit code и лог, SHA-256 итогового APK. Один commit, записанный после сборки в измененном дереве, не доказывает происхождение APK. Различие входных хешей или неуспешная команда не дают принятого receipt
- Install receipt проверяет SHA-256 установленного `base.apk` и однозначный ожидаемый package; фиксирует версию и certificate digest там, где доступна проверка. Неожиданные splits или невозможность проверить обязательную идентичность не обходятся молча. Повторная запись SHA исходного файла после adb install не заменяет проверку установленного артефакта
- Receipt подтверждает provenance конкретной сборки/установки, а не гарантирует bit-reproducible зависимости или одинаковый бинарный результат любой будущей сборки. Универсальный CI framework в этот объем не входит
- Fixture и live условия различаются явно: подставленные часы/координаты/provider нельзя описывать как реальные геолокацию или расписание. Неизвестные значения отмечаются `UNKNOWN`, а не угадываются; неизвестное обязательное условие не дает PASS
- Required scenario manifest фиксирует обязательные case IDs, условия, ожидаемые состояния и артефакты для конкретного этапа. Пропущенный, skipped, failed или не имеющий доказательства обязательный кейс делает общий gate неуспешным. Отсутствие отчетов, ноль выполненных тестов и частичный повтор не считаются полным успехом
- Каждый case result содержит фактический результат, причины ошибки и ссылки на PNG/XML/логи. Visual review хранится отдельно: reviewer, перечень наблюдений, принято/требует исправления. Capture success не означает visual acceptance

Decisive negative controls для самого runner, без изменения приложения:

| Контроль | Требуемый результат |
|---|---|
| Fixture XML чужого package | Отказ до действия и ненулевой exit |
| Два одинаковых подходящих enabled targets | Отказ из-за неоднозначности, не тап первого |
| Единственный target disabled | Отказ до действия |
| Postcondition не появляется до deadline | Timeout с состоянием и доказательствами, не PASS |
| XML before/after различаются состоянием плеера | Static capture не принят; dynamic режим не включается молча |
| Build-input hash до/после различается или Gradle завершился с ошибкой | Build receipt не принят, даже если старый APK остался на диске |
| SHA установленного/привязанного APK не совпадает с ожидаемым | Сценарий не принят |
| Required case отсутствует, skipped или без нужного PNG/XML | Итоговый gate неуспешен |

Проверяемый итог: правильный компактный corpus проходит, каждый из перечисленных неверных входов отвергается по ожидаемой причине. Проверки валидатора можно выполнять на fixtures без запуска устройства

Подход согласуется с [Iterating Development Workflows with Codex](https://developers.openai.com/cookbook/examples/codex/iterating-development-workflows-with-codex), опубликовано 2026-08-03, проверено 2026-11-08: отдельные наблюденные результаты и пропуски, адаптация к структуре проекта. Наличие дополнительных документов или агента само по себе не подтверждает качество

| `reader-meaning` | Объяснение относится к текущей части, движение на паузе |
| `reader-wait` | Понятно, почему текст ожидает следующую часть, доступно ручное действие |
| `reader-missing` | Пропущенное чтение не маскируется движением, есть понятный выход |
| `service-order` | Видны положение в порядке и способ перейти/вернуться |
| `search-error` / `search-empty` | Ошибка различима с отсутствием результатов, повтор понятен |

Основной набор: обычный телефон, обе темы, зафиксированные locale/timezone/font/density и данные. Для reader, формы и наиболее плотного экрана добавить область 320x640 dp с итоговым масштабом текста 2,6 и landscape 640x360 dp с масштабом 1,69. Фактические пиксели и density native устройства записываются отдельно. Это сочетания риска, а не требование перемножить все настройки каждого экрана

Критерии существующих Compose geometry/text-layout checks, дополненных ручным нативным просмотром: критичные кнопки и заголовки не обрезаны; действия доступны; размер касания не меньше 48 dp; reader сохраняет предусмотренную доступную область текста; selected/disabled/paused соответствуют сценарию. Длинная молитва может не помещаться целиком, но весь текст должен быть достижим прокруткой

Python+adb runner проверяет только явно наблюдаемые postconditions. Bounds и текст в XML сами по себе не доказывают отсутствие clipping, фактический размер касания 48 dp или достижимость всего текста. Автоматический accessibility PASS по одному XML запрещен

Ручные критерии: храм, расписание, основное действие и вспомогательные действия воспринимаются отдельными зонами; на reader первыми считываются часть, текст и управление; объяснение не выглядит частью молитвы; понятно, что приблизительно, что подтверждено и как исправить положение. Выбранный режим и активная фраза обозначены не только цветом

Контраст фактических цветовых пар: 4,5:1 для обычного текста; 3:1 для крупного текста и значимых графических элементов. Проверить обе темы и состояния active/disabled с учетом назначения. Требования и размер касания: [Android accessibility design](https://developer.android.com/design/ui/mobile/guides/foundations/accessibility), проверено 2026-11-08

Baseline принимает reviewer после просмотра. Новое изображение не становится эталоном автоматически; pixel-perfect сравнение само по себе не доказывает удобство. Существующих instrumentation/native screenshots достаточно для этого этапа. [Compose screenshot testing](https://developer.android.com/studio/preview/compose-screenshot-testing), проверено 2026-11-08, предупреждает, что standalone `com.android.compose.screenshot` больше не поддерживается, и предлагает AGP test suites 9.5+. На странице также остаются experimental flags прежнего плагина. Менять текущий стек перед выпуском ради этой интеграции не требуется

Compose ATF начинается с 1.8.0, а текущий проект использует Compose 1.7.3. Пока сохраняем геометрические проверки и дополняем ручным TalkBack, если доступен. Отсутствие TalkBack фиксируется отдельно. [Compose accessibility testing](https://developer.android.com/develop/ui/compose/accessibility/testing), проверено 2026-11-08

## Приоритет 3, P1: приемка итогового release APK и реального восстановления

Debug instrumentation и детерминированные часы остаются отдельным полезным слоем. Перед передачей APK требуется фактическая цепочка на окончательном release, с его SHA в evidence:

1. Чистая установка -> выбор храма -> текущая/следующая служба или отсутствие расписания -> текст
2. Play с настоящим ходом времени -> скорость -> оригинал/русский -> смысл -> возврат. Проверить видимое движение и предусмотренную паузу, не только значение подставленных часов
3. Фон, блокировка, возврат через Recents и поворот. Позиция сохраняется, продолжение соответствует контракту: движение только в видимом SERVICE при RESUMED, возврат не включает Play сам
4. Force-stop -> отключенная сеть -> холодный запуск. Сохраняются храм, настройки и принятая позиция; приложение открывается на паузе
5. Опубликованный 0.4 -> заполнение настроек и позиции через UI -> установка 0.5 поверх без очистки -> проверка сохранности. До установки сохранить evidence исходного состояния, APK и certificate digest. Для новой модели старый offset сбрасывается по документированному контракту, фраза сохраняется при наличии соответствия
6. Настоящий системный отказ в геолокации и выключенное местоположение. Ручной поиск/выбор остается рабочим; подставленные координаты помечены как fixture
7. Недоступное распознавание речи. Есть ручной путь; приложение не утверждает, что синхронизация выполнена
8. Финальный smoke на минимальном API 26 и основном API 35. Последняя публичная Android проверяется отдельно при доступной среде; отсутствие прогона не превращается в заявление о совместимости. Проверка совместимости не требует одновременной смены targetSdk

Сценарии upgrade и cold process не заменяются прямой записью подготовленных SharedPreferences. Для барьера Missing/End и точной математики остаются независимые unit/instrumentation проверки; native corpus дополняет их наблюдаемой цепочкой

В release evidence включить ошибки/ANR целевого приложения за время сценария. Не относить любой системный logcat warning к дефекту приложения. Не заявлять проверку физического телефона или точность реального хора без таких наблюдений

[Android Core app quality](https://developer.android.com/docs/quality-guidelines/core-app-quality), проверено 2026-11-08, включает сохранение состояния, фон/сон/повороты, доступность и совместимость. Требования к аудиоплееру не переносятся механически на текстовый плеер Феории

## Приоритет 4, P2: доказать чувствительность ключевых проверок

Существующая fault injection хранения уже содержательна. Для проверки способности harness обнаружить поломку достаточно трех изолированных мутаций, без нового mutation framework и без изменения рабочего устройства:

| Временная мутация в отдельной копии | Ожидаемое обнаружение |
|---|---|
| Убрать защиту от устаревшего поколения плеера | Конкретный тест late/stale event падает по ожидаемому assertion |
| Разрешить tick через MissingReading | Конкретный тест барьера падает по ожидаемому assertion |
| Вернуть автоматический храм при первом запуске | Конкретный FirstVisit/resolver test обнаруживает неявный выбор |

Для каждого контроля заранее назвать ожидаемый test ID и нарушение. Compile failure, ошибка окружения или посторонний timeout не считаются обнаружением мутации. После восстановления чистого кода повторить baseline. Отчет: мутация -> ожидаемый тест -> фактическая причина падения -> чистый повтор

Спорные UI failures проверяются на той же сборке native, как случай dialog registry выше. Независимое Astra review проверяет рассуждение и код, но не заменяет выполнение сценария и не является автоматическим visual judge

[Harness-aware evaluation of plugins](https://developers.openai.com/cookbook/examples/partners/harness_aware_plugin_evals/harness_aware_plugin_evals), опубликовано 2026-09-23, проверено 2026-11-08: результаты разных уровней fidelity не взаимозаменяемы, агрегатный score может скрыть изменения отдельных кейсов, model judge нуждается в проверке. Применение к Android здесь - инженерный вывод аудита, а не готовая Android методика из статьи

## Измерения и работа агентов

Перед выпуском полезны наблюдения startup, видимых задержек и ошибок в одинаковых условиях. Числа эмулятора не становятся обещанием быстродействия телефона. Новый Macrobenchmark module оставляем отдельной работой, если есть наблюдаемая проблема или доступное физическое устройство: [Macrobenchmark overview](https://developer.android.com/topic/performance/benchmarking/macrobenchmark-overview) и [Benchmarking in CI](https://developer.android.com/topic/performance/benchmarking/benchmarking-in-ci), проверены 2026-11-08. Официальная документация предупреждает о зависимости измерений эмулятора от host

Для оркестрации достаточно цикла: конкретный дефект -> воспроизводимый сценарий -> изменение -> независимое ревью -> повтор и сохраненное доказательство. Делегированный результат не принимается только по сообщению автора. Блокеры, skipped и прежние результаты остаются явно помечены
