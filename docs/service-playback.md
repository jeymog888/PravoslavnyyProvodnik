# Единый плеер: чистая модель

Этап 3.1 добавляет модель без изменения пользовательского runtime. `ServicePlaybackPlan` строится один раз для принятой даты и существующего каталога. `ServicePlaybackEngine` не зависит от Android, wall clock, UI, языка и хранилища

## Построение плана

`ServicePlaybackPlan.build(stages, serviceDate, readingDay)` сортирует этапы по order и получает треки через существующий `PrayerTrackFactory`

- `Text(stageId, trackId, lineId, durationBaseMillis)` - одна каноническая строка
- `Wait(stageId, durationBaseMillis)` - оставшаяся редакционная оценка этапа
- `MissingReading(stageId, serviceDate)` - блокирующая пауза после доступного вступления, когда для даты нет Апостола или Евангелия
- `End(stageId)` - конец путеводителя, не доказательство окончания реальной службы

Для строки берется оригинал, а при его отсутствии русский текст. Число слов считается по разделителям, включая неразрывные и другие Unicode-пробелы. Токены только из пунктуации не считаются словами. Продолжительность равна `max(4000, 500 * N)` мс. Это стартовый темп чтения, а не измерение хора

Для обычного этапа `C` - сумма интервалов текста, `D` - редакционные минуты этапа, `W=max(0,D-C)`. Доступный текст не обрезается и не растягивается. Если нет текста вообще, этап имеет один Wait, например подготовка. Если нет чтения дня, после вступления стоит MissingReading вместо автоматического ожидания. Чтение другой даты считается отсутствующим

Вход из расписания начинает выбранный этап с начала доступного фрагмента и с полным его бюджетом. Остаточное время редакционной оценки расписания не используется: оно не позволяет определить произносимую строку. Вход и ручная поправка всегда на паузе. Этот плеер не обещает акустической синхронизации

`contentVersion=1` обозначает версию семантики плана. SHA-256 `fingerprint` включает эту версию, дату, порядок сегментов, их идентичности, канонические строки и интервалы. Уточнение русского пересказа при неизменном оригинале не меняет временную позицию; изменение даты, исходника или временной структуры меняет fingerprint

Непустой каталог, уникальные ID/order и положительные бюджеты проверяются через `require`. Длительности суммируются с проверкой переполнения; весь план помещается в Long четвертей миллисекунды. Пустые/непригодные тексты, отфильтрованные `PrayerTrackFactory`, дают Wait либо MissingReading, но не пустой трек

## Состояние и время

`ServicePlaybackState` содержит fingerprint, индекс сегмента, пройденные четверти базовой миллисекунды, скорость и необязательный монотонный якорь. `isPlaying` выводится из наличия якоря

Скорости `SLOW`, `NORMAL`, `FAST` равны 3/4, 1 и 5/4. Один миллисекундный tick прибавляет соответственно 3, 4 или 5 четвертей базовой миллисекунды. Это исключает потерю дробей при частых обновлениях. `changeSpeed` сначала материализует время со старой скоростью, затем меняет множитель без пересчета накопленной позиции

- `start(stageId, speed)` - начало этапа на паузе
- `tick(state, nowMonotonicMillis)` - материализовать движение
- `play`, `pause`, `changeSpeed` - команды, учитывающие текущий tick
- `seekStage`, `seekLine` - явная ручная поправка с нулевым смещением и паузой
- `continueAfterMissing` - явное продолжение за отсутствующее чтение; действие должно вызываться отдельной кнопкой пользователя и оставляет следующую позицию на паузе

Большой tick может перейти через несколько текстов и Wait, но всегда останавливается на первом MissingReading или End. Остаток времени отбрасывается. Play не проходит ни один из этих сегментов. На End повторное начало требует явного seek

При обратном ходе монотонных часов tick ставит паузу на последней материализованной позиции. Повторный Play уже играющего состояния не перезапускает часы после такой ошибки. Отрицательный timestamp не запускает проигрывание. Умножение огромного delta насыщается Long.MAX_VALUE; поскольку общая длина плана проверена, это корректно означает достижение ближайшего барьера или конца

Runtime-состояние другого плана или с невозможной позицией отвергается через `require`. Поврежденные сохранения обрабатываются отдельно, через nullable restore

## Сохранение и интеграция следующего этапа

`snapshot(state, nowMonotonicMillis)` сначала учитывает foreground-время, затем возвращает `ServicePlaybackSnapshot(contentVersion, planFingerprint, segmentIndex, elapsedQuarterMillis, speed)`. В snapshot нет монотонного timestamp и флага проигрывания. `restore(snapshot)` возвращает паузу либо null, если версия, fingerprint или позиция не подходят

Владелец UI должен отдельно привязать snapshot к `ReadingContext`, сохранять его и ставить runtime на паузу при уходе в фон, другой экран, смысл, поиск и уточнение. Метод snapshot сам по себе не изменяет исходный immutable runtime-state. Эти обязанности не добавляются скрыто в чистую модель

Для UI доступны `indexOfStage`, `indexOfTrack`, `indexOfLine`, `stageAt`, `track`, `line`, `nextStageIndex`. `retainedTextAt` возвращает текущую или последнюю строку этого же этапа на Wait/MissingReading/End; у подготовки без текста возвращает null. Wait должен сохранять текст, смысл, ориентиры и ручной переход, а не показывать пустой таймер. Миграция старой фразы может использовать ID трека/строки; политика миграции остается у владельца хранилища

## Самопроверка

28 целевых unit-тестов покрывают канонический темп, Unicode-пробелы, редакционный остаток, длинный текст, реальные ресурсы и даты, уникальные позиции, дробный ход, смену скорости, границы сегментов, огромные delta, блокирующие паузы, неверные snapshot и повторный запуск

При чтении реализации найден реальный дефект: повторный Play после обнаруженного обратного хода часов мог тут же снять защитную паузу. Исправлено идемпотентным Play для уже играющего состояния; добавлена отдельная регрессия. Gradle и нативные проверки выполняет оркестратор, результаты записываются отдельно
