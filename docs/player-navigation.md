# Подключение единого плеера

AppNavigation содержит один ServicePlayerState на время жизни своей композиции. Смена этапа, даты, языка и темы не пересоздает его. Часы внедряются отдельным monotonicMillis, по умолчанию SystemClock.elapsedRealtime; wall clock остается для расписания и даты главного экрана

## Восстановление

Новый snapshot имеет приоритет перед stage_id и старой session. Его контекст, дата, fingerprint и позиция проверяются до создания owner. Успешное восстановление ничего не записывает при простом показе главного экрана и всегда paused

Поврежденный или несовместимый новый snapshot ведет к явному выбору службы на главной, без повторной legacy-миграции. Отсутствие обязательной metadata при существующем новом snapshot тоже считается поврежденным состоянием

При отсутствии нового ключа старая session используется только как адрес сохраненного этапа и источник миграционного предположения о дате. Старый autoAdvance не двигает этап по wall clock. Legacy-кандидат принимается атомарно при открытии сохраненного чтения. Восстановление прямо в SERVICE сначала выполняет то же принятие, затем показывает reader

Если у сохраненного этапа нет пригодной даты, главная явно сообщает об открытии на сегодня. Новая дата выбирается при действии пользователя. Закладки мигрируют адресно, старый offset не переносится

## Движение и выходы

Единственная coroutine плеера работает при SERVICE + RESUMED + playing и использует захваченный generation. В ней нет finally с записью старого состояния. ON_PAUSE, ON_STOP и dispose вызывают pause текущего стабильного owner; возврат lifecycle ничего не запускает

Все навигационные выходы проходят через pause до смены экрана. Открытие внешнего источника и настроек звука тоже ставит паузу. Уточнение запоминает факт работавшего плеера перед остановкой, чтобы показать соответствующую подсказку

Writer получает единственный monotonic timestamp команды. Он сохраняет snapshot, контекст, текущую закладку и marker с autoAdvance=false и нулевым старым offset. Состояние Main обновляется только после успешной записи. Текущий этап берется из owner, а не из старого ServiceSessionEngine.position

Поиск сначала находит track.id и line.id в плане принятой даты, затем принимает всю позицию одной транзакцией. Отдельной записи lyric keys после принятия больше нет. Отмена уточнения сохраняет paused позицию и вкладку; принятие открывает текст найденного места

## Завершение и смена храма

ReadingAcceptanceStore.clearReading(nextChurchId?) удаляет context, snapshot, marker, stage_id и все закладки одним Editor. При переданном nextChurchId новый храм записывается в тот же Editor. При ошибке выполняется штатный ограниченный rollback, а интерфейс остается на прежнем контексте с остановленным плеером

forgetAccepted вызывается только после успешного clear. При выборе найденного через discovery храма переход на экран храма также зависит от успеха atomic выбора; успешное добавление записи в каталог само по себе не означает успешную смену текущего чтения

Пять unit-проверок покрывают завершение, смену храма, откат после изменения памяти, повторную ошибку диска и отклонение некорректного ID

Restore пересчитывается по revision успешной записи, даже если при фиксированных часах context и marker равны прежним. Поврежденный snapshot после явного нового принятия не остается закэшированной ошибкой

Нажатия строк и текстов адресованы стабильными track/line ID и захваченным generation, а не индексом в изменяющемся текущем тексте. Все команды owner могут отклонить старое поколение до паузы или записи. UI также ограждает навигационные действия от предыдущего чтения
